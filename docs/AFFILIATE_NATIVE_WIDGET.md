# VOY PRO affiliate booking widget — pilot v1

The native widget is a **first-party page component installed on an approved affiliate website** (not an iframe). It displays real-time Budapest departures and server-calculated affiliate prices; creates/reprices booking holds with the canonical FBM public API; and confirms pay-on-arrival bookings **without leaving the affiliate page**. If Stripe online card payment is enabled by FBM, only the secure Stripe checkout redirects away. It does **not** create a second pricing, reservation or payment engine.

## Installation (per approved partner)

Place the mount and script on the affiliate page. Replace all capitalized placeholders with a specific partner's approved values; **do not publish example placeholders as functioning credentials**:

```html
<div id="voy-affiliate-booking"></div>
<script
  defer
  data-voy-affiliate-widget
  data-target="voy-affiliate-booking"
  data-affiliate="YOUR_PARTNER_COUPON"
  data-api-root="https://YOUR_APPROVED_FBM_API_HOST"
  data-client-key="YOUR_PUBLIC_BROWSER_CLIENT_KEY"
  src="https://voy-pro.com/assets/affiliate-booking-widget.js"
></script>
```

The recommended installation uses `defer`, with the target element in the
same page. The script also handles synchronous loading from `<head>` before
the target is parsed: it waits until `DOMContentLoaded` and then mounts.
The target **must exist by that event**; arbitrary late insertion by a
single-page-app framework is not an accepted integration path.

If a CMS injects the same script twice for one target, only the first mount
owns its closed Shadow DOM and booking session. Do not use duplicate script
tags to change the coupon, client key or API origin. For multiple distinct
booking widgets, use distinct `data-target` containers and independently
approved partner configuration. The intended partner pilot should still
install the script once.

- `data-affiliate` is the affiliate's exclusive coupon code, generated by FBM Affiliates management. It determines **both** the customer discount and the booking's `affiliate_id`. The widget never offers a second coupon.
- `data-api-root` is the HTTPS origin serving the **same environment** as the supplied client key (Staging for tests; the intended live FBM origin after release). Never mix a Staging key with Production API.
- `data-client-key` is an **intentionally browser-public** scoped key issued/registered in `public_booking_clients`. It is *not* a Supabase service-role, management bearer or Stripe secret.
- **Before publishing**, an administrator must approve the affiliate's exact website origin (scheme + host + port, if applicable) in that FBM public client's `allowed_origins`. `https://www.partner.example` and `https://partner.example` are separate origins. The FBM route rejects unlisted origins; CORS preflight itself need not authenticate.
- Disable/revoke a partner coupon and/or the client's origin when their agreement ends. Existing bookings are unaffected by changing the code.
- Register client-key domain restrictions, partner-code ownership and any privacy/data-processing agreement via the normal back-office approval process. A script widget lives in the host site's JavaScript environment: **the affiliate's site operator must be trusted** to handle forms on its own page. For untrusted partners or stricter isolation use the existing VOY PRO referral link rather than a native widget; a separately reviewed cross-origin isolated booking iframe could be developed later.
- Keep the script `src` HTTPS. CSPs on partner sites must allow this script and `connect-src` to the approved FBM API origin. The widget uses Shadow DOM to avoid leaking its CSS into the host page, has no permanent page-wide event handlers (only a one-time `DOMContentLoaded`
  listener if its target is not yet parsed), never writes
  cookies/localStorage/sessionStorage and never places customer data in a query string.
- No change is needed to global `X-Frame-Options: DENY` or deployment security headers.

## Flow

1. Validate approved configuration; fetch active experiences and online payment capabilities.
2. Collect the experience, date, independent riders (16+), child/baby passengers, private option and preferred guide language.
3. Call FBM real-time availability. Immediately sellable departures can be confirmed directly. **Nonprivate departures requiring staff approval** can now submit a pending Request to Book; they are not booked or paid. Private-group staff-confirmation departures still need direct VOY PRO assistance.
4. Validate this specific affiliate coupon against the selected departure. For immediately sellable departures, fetch the authoritative quote and fail closed if the applied affiliate attribution does not match. For staff-review departures, no final price is promised: the backend calculates the estimate as part of the approval request.
5. Create the canonical FBM hold; for private reservations, all subsequent quotes include that hold ID, to avoid falsely treating the reserved private departure as unavailable to its owner.
6. Load optional ancillary offers and update the canonical quote when quantities change. Release unconverted holds on changed selection; expire the form at the server-provided deadline.
7. Collect customer contact information and require explicit acknowledgement of the published VOY PRO Terms and Privacy Policy.
8. For immediately sellable departures, submit **one fixed affiliate coupon** and the verified quote's current hold to `/api/v1/bookings` with an idempotency key for pay on arrival; show booking confirmation on the partner page. If enabled, `/api/v1/payments/intents` starts an HTTPS Stripe checkout, and Stripe returns customers to the VOY PRO secure management page. For nonprivate departures requiring staff approval, submit the same fixed partner coupon to `/api/v1/booking-capacity-requests`, with **no hold, payment or ancillary sale**. Display a *request reference* rather than a confirmed booking, with explicit human-review messaging. All commission reporting uses FBM's central attributed booking/receipts data.

## English alternative — preparation only (currently OFF)

The embedded partner widget contains a dormant optional answer for whether
English would be comfortable if the **explicitly requested** guide language
cannot be provided. The distributed code has
`ENGLISH_ALT_PILOT_ENABLED=false` hardcoded. The question is hidden,
the input is disabled, and **no English-alternative preference is sent**.
Partner embed attributes, client key, URL parameters and WordPress cannot
enable this source-locked feature.

Only the isolated QA VM substitutes a test-only enabled copy of the script:
Yes maps to `true`, No to `false`, unanswered to `null`. The requested
language remains unchanged. Synthetic flows preserve the choice through
FBM hold/booking or pending staff request, verify the server echo, and show
the precise answer in the receipt. A change of requested language clears
the optional preference and invalidates previous availability.

This is **not a live affiliate feature or approval to use English instead
of the guest's preferred language**. Before an owner-approved switch of the
source flag, require authenticated Staging end-to-end tests of holds, bookings,
staff requests and exact-key retries, plus manager-verified guide skills,
7+ riders escort coverage, consent provenance, language changes,
multilingual copy and operational review. Do not activate in Production
or any WordPress installation until these gates are explicitly approved.

## QA / release gates

- `npm run build`, `npm run verify:launch` and `npm run qa:site` must pass.
- The site-wide QA executes `scripts/check-affiliate-booking-widget.mjs` with mock FBM endpoints. It verifies the embedded private booking, coupon lock, hold-aware re-pricing, ancillary selection and confirmed pay-on-arrival flow **plus a pending nonprivate staff request with no hold, booking or payment**. Chrome QA additionally verifies synchronous head loading and duplicate embed scripts on desktop/mobile. These tests make no live bookings or charges.
- Pilot one whitelisted domain, one real affiliate coupon, and isolated Staging checkout before approving activation on a production partner domain. Never install this widget from a Draft PR or unreviewed Staging build.
- Remaining release gates: the FBM affiliate-manager installer (#792) remains draft; provisioning of partner-dedicated public clients and approval of exact website origins still needs authorized configuration, optional multilingual UI is not implemented, and private-group staff approval is handled directly. The FBM origin/coupon binding (#795) is implemented for partner-bound clients, but browser-public keys and Origin headers cannot prove website identity to non-browser callers. Use partner-site contracts and the regular security review before real deployment.
